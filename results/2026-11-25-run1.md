## 실험 1. 세션 객체 저장과 조건부 갱신

조건: `state == "ACTIVE"` 이고 `authVersion == 기대값` 일 때만 `lastSeenAt`을 쓴다. 세션 1만 개, 필드 8개(actorKind, actorId, purpose, state, authVersion, issuedAt, expiresAt, lastSeenAt).

### 측정 결과

**코드와 동작**

| 구현 | 코드 (주석·빈 줄 제외) | 왕복 | 원자성 | 실패 사유 구분 |
| --- | --- | --- | --- | --- |
| Hash + Lua (`session-touch-hash.lua`) | 13줄 | 1 | 스크립트 전체 | `NOT_FOUND` / `REJECTED STATE` / `REJECTED VERSION` |
| JSON + Lua (`session-touch-json.lua`) | 14줄 | 1 | 스크립트 전체 | 위와 같음 |
| JSON 단독 (`JSON.MERGE` + 필터 경로) | 명령 1개 | 1 | 명령 1개 | 아래 표 참고 |

**JSON 명령만으로 해 본 결과** (`raw/2026-11-25/1-session.log`)

| 명령 | 상황 | 응답 |
| --- | --- | --- |
| `JSON.SET k $.lastSeenAt 1 NX` | 필드 있음 | `(nil)` — NX/XX는 경로 존재 여부만 본다 |
| `JSON.SET k $.lastSeenAt 1 XX` | 문서 state가 BLOCKED | `OK` — 값 조건 없이 써 버린다 |

| 같은 명령, 문서를 `{"s":{...}}`로 감쌈 | 조건 일치 | `OK`, 필드 두 개(`lastSeenAt`, `device`)를 한 번에 씀 |

| 〃 | 키 없음 | `ERR new objects must be created at the root` |
| `JSON.NUMINCRBY k '<필터>.lastSeenAt' 1` (감싼 문서) | 일치 / BLOCKED | `[1764000999001]` / `[]` |

**메모리 (세션 1만 개, 형태마다 빈 DB에서 따로 적재)**

| 형태 | `MEMORY USAGE` 합계 (키당) | `used_memory` 증가 (키당) | 비고 |
| --- | --- | --- | --- |
| Hash | 1,905,776 B (190 B) | 2,703,912 B (270 B) | 인코딩 `listpack` |
| JSON | 3,040,000 B (304 B) | 2,887,512 B (288 B) | `JSON.DEBUG MEMORY` 256 B |
| JSON 감싼 문서 | 3,760,000 B (376 B) | 3,664,352 B (366 B) | |

**처리량 (키 1만 개 무작위, 조건 항상 일치)**

| 구현 | P=1 rps | P=1 p50/p99 | P=16 rps | P=16 p50/p99 |
| --- | --- | --- | --- | --- |
| Hash + Lua | 148,810 (145k~151k) | 0.279 / 0.543 | 288,184 (279k~288k) | 2.695 / 3.567 |
| JSON + Lua | 84,104 (80k~85k) | 0.567 / 0.887 | 115,473 (114k~117k) | 6.815 / 8.175 |
| JSON 단독 `JSON.MERGE` 필터 | 67,751 (67k~68k) | 0.703 / 1.071 | 89,286 (84k~89k) | 8.839 / 10.543 |
| 기준선 `HSET` (조건 없음) | 231,481 (231k~256k) | 0.111 / 0.399 | 990,099 (952k~990k) | 0.735 / 1.423 |
| 기준선 `JSON.SET` (조건 없음) | 184,843 (176k~186k) | 0.231 / 0.447 | 406,504 (397k~407k) | 1.879 / 2.343 |

### 해석

- JSON 명령만으로도 "값 조건 + 여러 필드 쓰기"를 한 명령·한 왕복·원자적으로 할 수 있었다. 단 조건은 필터 경로(`$[?(...)]`)로만 걸 수 있고, 필터가 루트의 자식에 적용되므로 **문서를 한 단계 감싸야** 했다. 감싸면 키당 메모리가 약 70 B 늘었다.
- 필터가 맞지 않으면 버전 불일치와 BLOCKED가 똑같은 `Err wrong static path`로 오고, 키 없음은 다른 에러 문구로 온다. 거절 사유를 구분하거나, 가드 키처럼 다른 키도 함께 확인하거나, 최초 생성 같은 분기가 필요하면 여전히 Lua/Function 안에서 `JSON.*`를 불러야 한다. 프로젝트의 `issue-session.lua`는 이런 분기(가드 생성, `UNAVAILABLE` 사유, 토큰 충돌)가 있어 JSON 단독으로는 옮길 수 없다고 본다.
- 이 실험에서 JSON 단독(필터)이 JSON + Lua보다 느렸다(3회 모두). 매 호출 필터 경로를 해석·평가하는 비용으로 짐작하지만 원인은 측정하지 않았다.
- Hash + Lua가 처리량·메모리 모두 가장 유리했다. 필드가 평평한 세션에는 Hash가 맞고, JSON은 중첩 구조나 부분 조회가 필요할 때 이점이 있다. 이 실험은 평평한 객체라 JSON의 장점이 드러나지 않는 조건이다.
- 클라이언트에서 Lua 없이 조건부 갱신을 하려면 `WATCH` → `GET` → `MULTI` → `SET` → `EXEC`로 왕복이 여러 번 필요하다. 이 방식은 이번에 측정하지 않았다.

## 실험 2. 중복 요청 감지: Set vs Bloom filter (+ Cuckoo)

요청 ID `req-000000000000` ~ `req-000000999999`(16바이트) 100만 개를 서버 안 Lua 루프로 넣었다. Bloom: `BF.RESERVE 0.001 1000000`(기본 EXPANSION 2). Cuckoo: `CF.RESERVE 1000000`(기본 BUCKETSIZE 2), 넣을 때 `CF.ADDNX`.

### 측정 결과

| 항목 | Set | Bloom | Cuckoo |
| --- | --- | --- | --- |
| 새로 추가로 판정된 수 / 100만 | 1,000,000 | 999,940 | 992,556 |
| 적재 시간 (Lua 루프, 3회 범위) | 1.8~2.0 s | 1.8~2.5 s | 1.7~2.5 s |
| `MEMORY USAGE` | 42,388,694 B | 1,977,664 B | 2,097,256 B |
| `used_memory` 증가 (RESERVE 포함) | 63,282,992 B | 2,141,144 B | 2,196,016 B |
| `*.INFO` | 인코딩 `hashtable` | Size 1,977,632 / filters 1 | Size 2,097,224 / buckets 524,288 / filters 2 |
| 넣지 않은 ID 10만 개 중 "있다" | 0 (0%) | 53 (0.053%) | 1,524 (1.524%) |
| 넣은 ID 10만 개 중 "있다" | 100,000 | 100,000 | 100,000 |
| 삭제 | `SREM` → 1 | `BF.DEL` → `ERR unknown command` | `CF.DEL` → 1 |

- 거짓 양성 수는 3회 모두 같았다(해시가 결정적이고 ID가 같으므로).
- Cuckoo: `CF.ADD`는 이미 있는 항목도 또 넣는다(1 반환). 두 번 넣은 항목은 `CF.DEL`을 두 번 해야 `CF.EXISTS`가 0이 됐다.

**처리량**

| 명령 | P=1 rps | P=16 rps | P=16 p50/p99 |
| --- | --- | --- | --- |
| `SADD` (빈 키에 추가) | 249,377 (232k~249k) | 1,000,000 (935k~1.04M) | 0.727 / 1.767 |
| `BF.ADD` (빈 필터에 추가) | 245,098 (245k~253k) | 1,098,901 (1.03M~1.12M) | 0.679 / 0.911 |
| `SISMEMBER` (100만 개 Set) | 235,849 (228k~239k) | 1,250,000 (1.09M~1.25M) | 0.591 / 0.903 |
| `BF.EXISTS` (100만 개 필터) | 224,719 (224k~227k) | 1,754,386 (1.64M~1.75M) | 0.415 / 0.615 |
| `CF.EXISTS` (100만 개 필터) | 222,717 (223k~229k) | 1,587,302 (1.59M~1.75M) | 0.439 / 0.751 |

### 해석

- 메모리는 Bloom이 Set의 약 1/21(`MEMORY USAGE`) ~ 1/30(`used_memory`)이었다. Bloom 크기 1.98 MB는 p=0.001, n=100만의 이론값(약 14.4비트/항목, 1.8 MB)과 가깝다. Set은 ID 길이에 비례해 커지지만 Bloom은 ID 길이와 무관하다.
- 실측 거짓 양성률 0.053%는 설정한 0.1% 이하였다. 다만 적재 중에도 60개가 "이미 있다"로 판정됐다. 중복 요청 차단에 Bloom을 그대로 쓰면 **처음 온 정상 요청 일부를 중복으로 거절**한다는 뜻이다. 그래서 Bloom은 "확실히 처음"을 빠르게 거르는 1차 필터로 쓰고, "있다"로 나온 경우만 Set/DB로 확인하는 구성이 일반적이다.
- Bloom은 삭제가 없어 시간창이 지난 ID를 뺄 수 없다. 만료가 필요하면 시간창별 필터 키를 만들고 키째 지우는 방식이 필요하다. Cuckoo는 삭제가 되지만 기본 설정에서 거짓 양성률이 1.5%로 Bloom보다 훨씬 높았고, 용량 100만에서 필터가 2개로 늘었다. `CF.ADD`의 중복 삽입 동작 때문에 중복 감지에는 `CF.ADDNX`를 써야 한다.
- 처리량은 P=1에서 모두 22만~25만 rps로 비슷했다. 같은 컨테이너의 벤치마크 클라이언트·왕복이 병목이라 명령 차이가 안 보인 것으로 본다. P=16에서는 `BF.EXISTS`가 `SISMEMBER`보다 높게 나왔지만, 이 차이가 실제 서비스에서 의미 있는지는 이 실험으로 말할 수 없다.

## 실험 3. 같은 요청 제한 로직: EVAL/EVALSHA vs FUNCTION/FCALL

`commerce/src/main/resources/redis/rate-limit.lua`를 그대로 `lua/rate-limit.lua`로, 같은 로직을 `lua/ratelimit-lib.lua`(`#!lua name=ratelimit`, `rate_limit` + 읽기 전용 `peek`)로 만들었다.

### 측정 결과

**정확성**: 한도 5에서 요청 1~5 허용, 6 거절. EVALSHA와 FCALL 결과가 같았다.

**처리량 (키 10만 개 무작위, 항상 허용)**

| 호출 | P=1 rps | P=1 p50/p99 | P=16 rps | P=16 p50/p99 |
| --- | --- | --- | --- | --- |
| `EVAL` (본문 337 B 매번 전송) | 134,953 (131k~135k) | 0.335 / 0.599 | 291,545 (285k~292k) | 2.607 / 3.447 |
| `EVALSHA` | 153,139 (153k~160k) | 0.279 / 0.615 | 362,319 (353k~362k) | 2.111 / 2.575 |
| `FCALL` | 168,634 (168k~172k) | 0.255 / 0.487 | 383,142 (380k~383k) | 1.983 / 2.391 |
| 기준선 `INCR` | 234,742 (228k~235k) | 0.111 / 0.327 | 1,388,889 (1.30M~1.39M) | 0.527 / 0.735 |

**수명**

| 시점 | `EVALSHA` | `FCALL` |
| --- | --- | --- |
| `SCRIPT FLUSH` 뒤 | `SCRIPT EXISTS` 0, `NOSCRIPT No matching script. Please use EVAL.` | 동작 (`1 60000`) |
| `FLUSHALL` 뒤 | (캐시는 유지) | `FUNCTION LIST`에 라이브러리 그대로, 동작 |
| `docker restart` 뒤 (AOF 켬) | 재시작 전 `SCRIPT EXISTS` 1 → 뒤 0, `NOSCRIPT` | 라이브러리 복원, 동작 |

재시작 뒤 `/data`: `appendonlydir/appendonly.aof.N.base.rdb`, `*.incr.aof`, `manifest`, `dump.rdb`.

**ACL**

| 사용자 권한 | 호출 | 응답 |
| --- | --- | --- |
| 기본 사용자 | `EVALSHA_RO <쓰기 스크립트>` | `ERR Write commands are not allowed from read-only scripts` (실행 중 6번째 줄에서) |
| 기본 사용자 | `FCALL_RO rate_limit` | `ERR Can not execute a script with write flag using *_ro command.` (실행 전) |
| `-@all +evalsha_ro +fcall_ro +get +pttl ~lab:rl:*` | `EVALSHA_RO <읽기 스크립트>`, `FCALL_RO peek` | 둘 다 동작 |
| 〃 | `EVALSHA_RO <쓰기 스크립트>` | `ERR ACL failure in script: ... no permissions to run the 'incr' command` |
| 〃 | `EVALSHA`, `FCALL` | `NOPERM` |
| `-@all +fcall +incr +pexpire +pttl ~lab:rl:*` | `FCALL rate_limit` | 동작 |
| 〃 | `EVAL`, `FUNCTION LOAD` | `NOPERM` |
| 〃 | `FCALL rate_limit 1 other:key` | `NOPERM No permissions to access a key` |
| `-@all +fcall +pexpire +pttl` (incr 없음) | `FCALL rate_limit` | `ERR ACL failure in script: ... 'incr' command script: rate_limit` |
| `-@all +eval +incr +pexpire +pttl` | 임의 Lua (`for` 루프 합계) | `500500` |

### 해석

- `FCALL`이 `EVALSHA`보다 P=1에서 약 7~10%, P=16에서 약 6~8% 높았고 3회 모두 순서가 같았다. 차이는 작고, 같은 Lua 엔진에서 같은 코드를 돌리므로 성능을 이유로 Functions를 고를 정도는 아니라고 본다. `EVAL`은 본문 전송·해시 계산 때문에 가장 느렸다.
- 실질적인 차이는 **수명과 관리 방식**이다. 스크립트 캐시는 재시작·`SCRIPT FLUSH` 뒤 비어 클라이언트가 `NOSCRIPT`를 받고 다시 올려야 한다. (장애 조치는 실험 7에서 확인: 캐시가 비지는 않지만 새 master에는 그 노드가 직접 올린 스크립트만 있다.) Functions는 데이터처럼 AOF/RDB에 저장되어 재시작 뒤에도 남았고, `FLUSHALL`로도 지워지지 않았다. 배포 때 `FUNCTION LOAD REPLACE`로 서버에 올리는 절차가 생긴다는 뜻이기도 하다.
- 읽기 전용 표시: Function은 `no-writes` 플래그로 등록 시점에 선언되어 `FCALL_RO`가 실행 전에 거절했다. `EVALSHA_RO`는 실행하다가 쓰기 명령을 만나야 거절했다.
- ACL은 함수 이름 단위로 나눌 수 없었다(`+fcall`이면 모든 함수). 대신 `+fcall`만 주고 `+eval`·`FUNCTION LOAD`를 막으면 "관리자가 올린 코드만 실행"이 되고, `+eval`을 주면 임의 코드를 보낼 수 있다. 스크립트·함수 안의 명령과 키도 호출자 권한으로 다시 검사되었다.

## 실험 4. 오래 도는 스크립트: BUSY와 KILL

`busy-reply-threshold`를 1000 ms로 낮추고 1.5초 뒤 다른 연결에서 명령을 보냈다.

### 측정 결과

| 상황 | 다른 연결의 `PING` | `SCRIPT KILL` | `FUNCTION KILL` | 원래 호출의 응답 |
| --- | --- | --- | --- | --- |
| `EVAL` 무한 루프 | `BUSY ... You can only call SCRIPT KILL or SHUTDOWN NOSAVE.` | `OK` | `BUSY ...` (거절) | `ERR Script killed by user with SCRIPT KILL...` |
| `FCALL spin` 무한 루프 | `BUSY ... You can only call FUNCTION KILL or SHUTDOWN NOSAVE.` | `BUSY ...` (거절) | `OK` | `ERR Script killed by user with SCRIPT KILL... script: spin` |
| `SET` 뒤 무한 루프 (`EVAL`) | `BUSY` | `UNKILLABLE Sorry the script already executed write commands...` | — | `SHUTDOWN NOSAVE` 뒤 `Server closed the connection` |

- `SHUTDOWN NOSAVE` 뒤 `docker start`로 다시 띄우자 `GET lab:busy:w`는 `(nil)`이었고, `busy` 라이브러리는 남아 있었다.

### 해석

- 두 방식 모두 실행 중에는 서버 전체가 다른 요청을 받지 못한다. Functions라고 격리되지 않는다.
- 멈추는 명령이 나뉘어 있다(`SCRIPT KILL`은 EVAL만, `FUNCTION KILL`은 함수만). 운영 도구·런북에 둘 다 있어야 한다. 함수가 죽었을 때 에러 문구에는 여전히 "SCRIPT KILL"이 찍혔다.
- 쓰기를 한 뒤에는 어느 쪽이든 원자성을 지키기 위해 죽일 수 없고, 남는 선택은 `SHUTDOWN NOSAVE`(프로세스 종료)뿐이다. 이번에는 끝나지 못한 스크립트의 쓰기가 재시작 뒤 남지 않았다.
