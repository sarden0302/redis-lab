# 2026-11-25 2차 측정: WATCH/MULTI/EXEC vs EVALSHA vs FCALL

[1차 측정](2026-11-25-run1.md) 실험 1의 해석에서 "WATCH 방식은 측정하지 않았다"고 남긴 부분을 채운다. 같은 조건부 갱신을 클라이언트 낙관적 잠금과 서버 쪽 Lua(EVALSHA, Functions)로 부르고 비교했다.

## 갱신 내용과 전략

조건: `state == "ACTIVE"` 이고 `authVersion == 3` 일 때만 `lastSeenAt`과 `touches`(읽은 값 + 1)를 쓴다. `touches`는 잃어버린 갱신을 세려고 실험 1의 `session-touch-hash.lua`에 더한 필드다(`lua/session-touch-count.lua`, `lua/session-lib.lua`). 측정 중에는 조건이 항상 맞는다.

| 전략 | 한 번 시도의 흐름 | 왕복 / 보낸 명령 |
| --- | --- | --- |
| `watch-multi` | `WATCH`+`HMGET` 파이프라인 → 클라이언트 판단 → `MULTI`+`HSET`+`EXEC` 파이프라인. `EXEC`가 nil이면 처음부터, 재시도 10회 뒤 포기 | 2 / 5 |

| `evalsha` | `EVALSHA <sha> 1 key 3 now` | 1 / 1 |
| `fcall` | `FCALL session_touch 1 key 3 now` | 1 / 1 |

### WATCH 흐름 기록 (`5-watch-vs-lua.log` 앞부분)

충돌이 없으면 왕복 2번이다.

```text
[A] 왕복 1: 명령 2개
  > WATCH lab:w:hot:0
  < OK
  > HMGET lab:w:hot:0 state authVersion touches
  < ["ACTIVE", "3", "0"]
[A] 왕복 2: 명령 3개
  > MULTI
  < OK
  > HSET lab:w:hot:0 lastSeenAt 1764000999000 touches 1
  < QUEUED
  > EXEC
  < [0]
```

A가 읽은 뒤 B가 같은 키를 갱신하면 A의 `EXEC`가 nil을 받고, A는 처음부터 다시 읽는다.

```text
[A] 왕복 1: 명령 2개
  > WATCH lab:w:hot:0
  < OK
  > HMGET lab:w:hot:0 state authVersion touches
  < ["ACTIVE", "3", "1"]
[B] 왕복 2: 명령 1개
  > EVALSHA 914becc8b83353e68d4db299d3cbd1b423f84e95 1 lab:w:hot:0 3 1764000999000
  < ["UPDATED"]
[A] 왕복 3: 명령 3개
  > MULTI
  < OK
  > HSET lab:w:hot:0 lastSeenAt 1764000999000 touches 2
  < QUEUED
  > EXEC
  < (nil)
[A] 왕복 4: 명령 2개
  > WATCH lab:w:hot:0
  < OK
  > HMGET lab:w:hot:0 state authVersion touches
  < ["ACTIVE", "3", "2"]
[A] 왕복 5: 명령 3개
  > MULTI
  < OK
  > HSET lab:w:hot:0 lastSeenAt 1764000999000 touches 3
  < QUEUED
  > EXEC
  < [0]
```

마지막 `touches`는 3(A 두 번 + B 한 번)이었다. 조건이 맞지 않으면(BLOCKED) `WATCH`+`HMGET` 뒤 `UNWATCH`로 끝나 왕복 2번, Lua는 `["REJECTED", "STATE"]` 왕복 1번이었다.

## 해석

- **정확성**: WATCH, EVALSHA, FCALL은 모든 칸에서 잃어버린 갱신이 0이었다. WATCH만 뺀 naive는 키 1만 개에서도 연결 8개부터 갱신을 잃었고(15~99건), 키 1개에서는 성공으로 센 갱신의 80~95%가 덮어써졌다. 읽고 판단하고 쓰는 흐름에서는 WATCH든 Lua든 원자성 장치가 꼭 있어야 하고, 이 검사가 그 차이를 실제로 잡는다는 것도 확인했다.
- **경합이 없을 때**: WATCH는 Lua의 약 절반 처리량(연결 1: 5~6k vs 9.5~11k/s), 약 2배 p50이었다. 왕복이 2배이고 명령 수가 5배인 만큼이다. 다만 이 수치는 클라이언트 CPU에 묶여 있어(아래 한계), 왕복 시간이 긴 실제 네트워크에서는 "왕복 2배"가 지연에 더 직접 드러날 것으로 본다.
- **경합이 있을 때**: WATCH는 연결이 늘수록 나빠졌다. 키 1개에 연결 8개에서 성공 1개당 EXEC 중단 4.1회, 논리 갱신 15%가 재시도 10회 뒤 포기, 성공/s는 Lua의 1/11. 연결 32개에서는 성공당 중단 16~20회, 절반 가까이 포기, p50 30 ms, 성공/s는 Lua의 1/40 수준이었다. 같은 키를 두고 다투는 상황(같은 계정의 동시 요청, 인기 상품 재고 등)에 WATCH 재시도는 맞지 않는다.
- **Lua는 경합에 둔감했다**: EVALSHA·FCALL은 키 1개든 1만 개든 처리량·지연이 같았다. Redis가 스크립트를 한 번에 하나씩 끝까지 실행하므로 충돌·재시도가 생기지 않는다. 대신 그 시간 동안 다른 명령이 기다리므로(실험 4) 스크립트는 짧아야 한다.
- **EVALSHA vs FCALL**: 모든 칸에서 범위가 겹쳤다. 실험 3(redis-benchmark)에서 본 FCALL의 5~10% 우위는 Python 클라이언트 비용에 묻혀 보이지 않았다. 둘 중 선택은 실험 3의 수명·관리 차이로 하는 것이 맞다고 본다.
- WATCH가 맞는 경우: Lua를 쓸 수 없는 환경(스크립트 금지 ACL 등), 읽은 값으로 하는 판단이 클라이언트 쪽 로직·외부 호출에 의존하는 경우, 그리고 경합이 거의 없는 경우. 이때도 포기 횟수와 실패 처리를 정해 두어야 한다.

## 한계

- 측정하는 동안(18:09~18:15) 같은 Docker Desktop에서 다른 실험 컨테이너(`rlab-split-*`, `rlab-cluster-*`)가 함께 돌았다. 칸마다 네 전략을 번갈아 재서 전략 사이 비교에는 영향이 고르게 들어갔다고 보지만, 절대값은 조용한 상태보다 낮거나 흔들렸을 수 있다.
- Python 클라이언트가 병목이다. Lua는 연결 8 → 32에서 처리량이 23k → 26k/s로 거의 늘지 않았고, redis-benchmark(실험 1, 같은 Hash + Lua로 15만 rps)의 1/6 수준이다. 처리량 절대값은 실험 1~4와 비교하지 않고 전략끼리만 비교한다. 왕복·명령이 많은 WATCH는 클라이언트 쪽 일도 많아 서버 비용 이상으로 불리하게 나왔을 수 있다.
- 클라이언트는 한 이벤트 루프에서 코루틴을 번갈아 돌린다. 실제 여러 앱 서버·스레드에서 동시에 보낼 때와 충돌 패턴이 다를 수 있다.
- 컨테이너 사이 왕복은 Docker Desktop VM 안이라 짧다. 왕복이 길어지면 WATCH 방식은 지연과 함께 읽기~EXEC 사이 충돌 창도 길어진다.
- WATCH 흐름은 `WATCH`와 `HMGET`을 한 번에 보내는 가장 유리한 형태로 쟀다. 재시도 사이 대기(backoff)는 넣지 않았다. backoff를 넣으면 포기는 줄겠지만 지연은 더 늘어난다.
- 높은 경합은 키 1개만 쟀다. 키 몇 개짜리 핫셋(`W_HOT_KEYS`)은 측정하지 않았다.
- 단일 노드다. 클러스터에서 여러 키를 WATCH하거나 스크립트에 넘기려면 같은 슬롯이어야 하는 제약은 다루지 않았다.
