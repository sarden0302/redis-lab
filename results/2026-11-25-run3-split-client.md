# 2026-11-25 3차 측정: 벤치마크 클라이언트를 별도 컨테이너로 분리

1차 측정([2026-11-25-run1.md](2026-11-25-run1.md))은 `redis-benchmark`를 Redis 서버와 같은 컨테이너에서 돌렸다. 클라이언트와 서버가 CPU를 나눠 써서 숫자가 왜곡됐는지 보려고, 실험 1~3의 처리량 부분만 클라이언트를 다른 컨테이너로 옮겨 다시 쟀다.

## 해석

**사실**

- P=1 처리량은 오르지 않고 모든 명령에서 8~29% 내렸다. p50은 대부분 0.03~0.09 ms 늘었다. 가벼운 명령(`HSET`, `SADD`, `INCR`, `BF.*`)은 1차 22만~25만에서 3차 17.6만~18.8만으로 내려 서로 거의 같아졌다.
- P=16에서 스크립트·JSON 명령(`EVAL`, `EVALSHA`, `FCALL`, Hash/JSON + Lua, `JSON.MERGE`)은 -3.1%~+3.7%로 1차와 사실상 같았다. 가벼운 명령은 5~14% 내렸다.
- CPU 제한을 없애도 결과가 같았다.
- 순위는 바뀌지 않았다.
  - 실험 1: P=1·16 모두 Hash + Lua > JSON + Lua > `JSON.MERGE` 필터, 기준선 `HSET` > `JSON.SET`.
  - 실험 3: P=1·16 모두 `EVAL` < `EVALSHA` < `FCALL` < `INCR`. `FCALL`의 `EVALSHA` 대비 우위는 P=1에서 1차 약 10% → 3차 약 5%(3회 범위는 겹치지 않음), P=16에서 약 6% → 약 7%.
  - 실험 2: P=1은 1차에도 22만~25만으로 붙어 있었고 3차에는 17.6만~18.2만으로 더 붙었다(차이가 반복 간 편차 수준). P=16은 두 번 모두 `BF.EXISTS`·`CF.EXISTS` > `SISMEMBER` > `BF.ADD`·`SADD`.

**짐작 (따로 측정하지 않음)**

- 1차에서 클라이언트·서버의 CPU 공유가 숫자를 깎았다는 가설은 이 결과로는 지지되지 않는다. 호스트 CPU가 32개라 한 컨테이너 안에서도 두 프로세스가 각자 코어를 썼을 것으로 본다.
- P=1 하락과 p50 증가는 컨테이너 사이 bridge 네트워크(veth) 왕복이 루프백보다 수십 µs 더 드는 탓으로 본다. P=1은 요청마다 왕복을 기다리므로 그대로 드러나고, P=16은 왕복 하나에 요청 16개를 실어 가려진다. 서버 처리 시간이 긴 스크립트·JSON 명령은 P=16에서 서버가 병목이라 차이가 없었다.
- 그래서 1차의 P=1 숫자는 "왜곡"이라기보다 왕복 비용이 거의 없는 조건의 값이다. 명령 사이 상대 비교와 결론(Hash + Lua 우세, `FCALL`이 `EVALSHA`보다 약간 빠름, 실험 2 P=1은 클라이언트·왕복이 병목)은 그대로 유지된다. 실제 서비스처럼 호스트가 다르면 왕복이 더 길어져 P=1 차이는 더 줄어들 것이다.

## 한계

- 같은 호스트의 Docker Desktop 안 bridge 네트워크다. 실제 네트워크 지연·대역폭은 반영하지 않는다.
- 반복 3회와 CPU 제한 없는 1회뿐이고, 측정 순서는 1차와 같아(실험 1 → 2 → 3) 순서 효과를 분리하지 않았다.
- 클라이언트를 분리한 효과(CPU 공유 제거)와 네트워크 경로가 바뀐 효과가 함께 섞여 있다. 같은 컨테이너 + CPU 고정(`--cpuset-cpus`)처럼 하나씩 바꾸는 측정은 하지 않았다.
